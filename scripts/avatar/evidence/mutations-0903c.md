# mutation 收據 2026-09-03（第六版，逐欄去趨勢版）

受測檔 `public/avatar/mika-milfy.vrm`，sha256 開頭 `66871116b6263fb9`，
vertex sha `ae7f90eecb9784d9`。

本檔取代 `mutations-0903b.md`。那一份是「整張往中位數收 85%」（`HAIR_EVEN`）
那個機制的收據；機制在同一天換成逐欄去趨勢（`HAIR_FLATTEN_BLOCKS`），舊收據裡
的每一個數字都失效，包括 M1 的紅燈訊息。舊檔留著只為了對照，別拿它的數字當現
況。

## 方法

每一次 mutation 都先斷言 pattern 在檔案裡剛好命中 1 次、且改寫後檔案內容真的
變了，再重建。**重建走完整的 `make.py`**（不是單獨呼叫 `build.py`），所以受測
的是 34 個材質的出貨檔，沒有「少 10 個材質」那種口徑差；上一份收據有那個限
制，這一份沒有。

還原用位元組副本（`shutil.copy`），不是 `git checkout --`：這一輪的修正還沒
commit，`git checkout` 會把修正一起抹掉。每一次驅動跑完都比對一次，`build.py`
與 `customise.py` 與副本逐位元組相同，出貨檔與 `out/mika-milfy.vrm` 都回到
`66871116b6263fb9`。

**有一格例外，要講清楚**：`mut4-0903f.log` 第 7–8 行，第一次 M11 那次驅動的還
原比對印的是 `byte-identical: False`（兩個檔都是）；同一份 log 第二次 M11 印的
是 `True`。副本已被後續的驅動覆蓋，回推不出當時差在哪一個位元組，所以這裡不編
造原因。能確定的是兩件事：同一行印的出貨 sha 仍是 `66871116b6263fb9`（那一次的
差異沒有走進輸出），而「現行原始碼產出的模型與出貨位元組等價」這件事後來由第四
次等價重建直接驗過（見下面那一節），不再依賴這一格。

驅動腳本與逐字輸出，每一個 mutant sha 都能在其中一份找到：

| log | 內容 |
|---|---|
| `mut-0903f.log` | M1–M10、S8、S32（第一輪，色帶那條當時只斷言暖度）；留檔 M1 → `probe-nofl.vrm`、M8 → `probe-old.vrm` |
| `mut2-0903f.log` | 補上明度斷言之後重跑 M1／M3／M4 |
| `mut4-0903f.log` | M11，含第一次選錯目標（252,210,196）那一次 |
| `mut5-0903f.log` | B1，留檔 → `probe-v5.vrm` |
| `mut6-0903f.log` | M2 與 B0 重跑並留檔 → `probe-even.vrm`／`probe-b0.vrm` |
| `mut7-0903f.log` | B0 再跑一次留檔（探針圖用的就是這一份）→ `probe-b0.vrm` |

`probe-*.vrm` 是給探針頁量測用的暫存檔，量完就刪，不進 repo。**本檔與
`colorprobe-0903.md` 引用的 M2 sha 是 `55b8a71b436076a2`（`mut6-0903f.log`）、
B0 是 `b4a83f5a4dfea7f7`（`mut7-0903f.log`）。**同一個 mutation 在不同次建置會
得到不同的位元組 sha（見 RESULT.txt「範圍外：建置的位元組不是決定性的」），所
以引用時一律用有 log 的那一次，不要拿早先跑過但沒留 log 的那次。

B0 跑過兩次、常數完全相同，`mut6` 那次是 `7ed54e5b287fa16f`、`mut7` 那次是
`b4a83f5a4dfea7f7`，兩次守門測試都紅在同一組數字（貼頭層暖度 81、自由段 31，差
50）。兩次都寫進同一個 `probe-b0.vrm`，而背面那六個框與
`evidence/back-v10-before.png` 都是 `mut7` 收工（03:09:31）之後才拍的，那一次載
入探針頁印在 `#out` 的 sha 也是 `b4a83f5a4dfea7f7`，所以引用一律指 `mut7`。（sha
只進頁面，PNG 檔本身不帶 sha。）

M1／M3／M4 有兩輪紀錄：第一輪那條測試只斷言暖度，M3 是綠的；補上明度斷言之後

## 後腦色帶：兩個面向、兩個斷言

`test_hair_reads_as_one_tone_from_scalp_to_tail` 比貼頭層與自由段的**暖度**
（上限 12）與**明度**（上限 0.02）。兩個都要，因為 `_flatten_v` 對飽和與明度
各去一次趨勢。現況：暖度 23.0 對 23.0 差 0，明度 0.8275 對 0.8275 差 0.0000。

| # | mutation | 暖度 | 明度 | 結果 |
|---|---|---|---|---|
| M1 | `HAIR_FLATTEN_BLOCKS` 16 → 0 | 40 對 16，差 **24** | — | **RED** |
| M3 | `_flatten_v` 只做飽和（拿掉明度那一行） | 差 8.5（過，見註）| 0.7922 對 0.8569，差 **0.0647** | **RED** |
| M4 | `_flatten_v` 只做明度（拿掉飽和那一行） | 34 對 20，差 **14** | — | **RED** |

M3 是加上明度斷言之前唯一全綠的那一格。只斷言暖度時它是綠的（暖度差 8.5 在上
限 12 以內），而畫面上枕骨與髮梢差 0.065 的明度是一條看得見的亮暗帶。

**8.5 這個值沒有 log 撐**：斷言通過時 unittest 不印任何數字，所以
`mut-0903f.log` 的 M3 那兩行只有 `GREEN`，`mut2-0903f.log` 印的是明度那條的紅燈
訊息。8.5 是當時另外量 M3 那份 mutant 的貼圖得到的，那份建置已經覆蓋掉，補不回
來。有 log 撐的是這一格的結論本身——「只斷言暖度時 M3 全綠、補上明度斷言後轉
紅」，兩份 log 逐字印著。要重新取得 8.5，得重跑一次 M3 建置。這就是
「N 道防禦要有 N 條斷言」的實例：兩行程式各去一個通道的趨勢，只釘一個通道等於
只釘一半。

`test_skin_texture_keeps_visible_tone_under_mtoon_lighting`：Body 與 Face 貼圖

| # | mutation | 結果 |
|---|---|---|
| M6 | `SKIN_TARGET` 退回 (244,190,172) | **RED** 最亮通道 244 < 245 |
| M7 | `SKIN_TARGET` → (252,200,180)（一樣亮，但偏橘） | **RED** 暖度 73 > 48 |
| M8 | `HAIR_SAT, HAIR_LIFT` 退回 0.75, 0.0 | **RED** 最亮通道 206 < 215 |
| M9 | `HAIR_SAT` → 1.20（保持提亮，飽和拉高） | **RED** 暖度 43 > 30 |

M8 對色帶那條測試是綠的（它保留逐欄去趨勢），這正好證明兩件事互相獨立：髮色的
深淺與色帶的均勻是兩個機制，各自的守衛不會互相頂替。

## 註解改動之後的等價檢查

出貨位元組產出之後，原始碼還動過三批：`build.py` 的常數註解、
`customise._flatten_v` 的 docstring，以及 **03:05 那次把 `np.errstate` 換成
`warnings.catch_warnings()`**。前兩批是說明文字；第三批是可執行的敘述（多了
`import warnings` 與一個 `with` 區塊），只是它的作用僅止於把 numpy 的
`All-NaN slice encountered` 靜音，不碰任何像素。為了不讓「gate 跑的是舊程式」這
件事成立，改完就把整份 `make.py` 重跑一次比對，前後共五次（改動批次與重建次數不
是一對一，中間有補跑）。第五次是最後一次：04:14–04:20 依 review 意見又改過
`appearance_test.py`、`build.py`、`customise.py` 三個檔的註解與 docstring（都是為
了更正量不回來的數字），改完再跑一次把收據補齊。

**這張表哪幾格有 log 撐、哪幾格沒有，要分清楚。** `make.py` 只印
`vertex sha`，不印檔案 sha、不比貼圖、不比算圖，所以前兩列的 log 欄位只撐得起
`vertex sha` 那一格；建置 sha、43 張貼圖、算圖比對三欄是當時另外跑比對得到的，
數字沒有寫進任何一份 log，現在回頭查不到出處。第四列不一樣：
`build-0903h-equiv3.log` 是比對腳本自己的輸出，六格全部印在那份 log 裡。要單獨挑
一列當收據，挑第五列——它的六格全部印在 `build-0903j-equiv5.log` 裡，而且是唯一
四張約定機位算圖都比過的一次（第四次只比到兩張，原因見下）。

讀第四列那份 log 有一個會絆人的地方：裡面有兩行都叫「vertex sha」，值不一樣。首
尾兩行的 `ad416c3fad31819e` 是比對腳本自己算的（只雜湊每個 primitive 的 POSITION

另外，前兩列「算圖差異像素 0」很可能帶著與第四列同一個限制（比對腳本的機位名單
寫成 front／back／left／right），但那兩次沒有留下輸出，無法確認涵蓋幾張，所以這

第三次那一列要照實說：它跑過、也還原成出貨位元組，但**沒有留下建置輸出**，sha 只
存在於本輪的交接筆記裡，等價比對的三個欄位都沒有記錄。它留下的唯一痕跡是出貨對
與 `mika-milfy.parts.json` 一度是 03:10:48 的 mtime——那是第二輪 reviewer 在我做
第四次重建之前查到的，第四次與第五次的還原已經把那批 mtime 覆蓋掉（現在是
04:22:07）。它證明不了
任何事，列在這裡是為了讓重建次數對得起來，不是拿來當收據。

第四次是補的，補的正是前三次蓋不到的那一段：`catch_warnings` 那次改動發生在
02:34 之後，所以前兩份 log 都證明不了現行的 `customise.py`——它們的第一行到現在
都還印著那個 `All-NaN slice encountered`（分別指向 `customise.py:441` 與

五次都在比完之後把出貨檔換回 `66871116b6263fb9`，讓所有 gate log、mutation 收據

獨跑 `render.py` 重新產生，這是它們現在的來源，也與 RESULT.txt 的說法一致。第四

## 頸縫：兩張貼圖必須落在同一個膚色

`test_neck_seam_keeps_one_skin_tone_across_two_textures` 取兩個網格真正相鄰
（2mm 內）的頂點，各自把自己的 UV 取樣進自己那張貼圖，比兩側中位數的 CIE76
ΔE，上限 3.0。量法不含打光：下巴下方本來就在陰影裡，畫面上那條深淺差是打光造
成的，與貼圖對不對得上無關。現況縫上臉側 (251,208,196.5)、身側 (251,206,194)，
ΔE **1.04**；`baseline.vrm` 是 (228,144,147.5) 對 (189,112,133)，ΔE 15.77。

這兩個 ΔE 取的是中位數的**浮點值**，與斷言評估的是同一個量。把中位數截斷成整
數再算會得到 0.97 與 15.93——那是兩種不同的量，別混著引用。測試的失敗訊息因此
也改成印到小數一位。

| # | mutation | 結果 |
|---|---|---|
| M11 | 身體那張改解到 (252,216,208)，臉仍解到 `SKIN_TARGET` | **RED** 縫上 ΔE 4.38 |

這一格是這一輪新增的守衛。`retone` 把兩張貼圖解到同一個 `SKIN_TARGET`，就是為
了讓這條縫關著，而那個設計原本沒有任何斷言看著：所有膚色斷言都以「單張貼圖的
中位數」為指標，換掉其中一張的目標，每一條都還是綠的。M11 特意挑一個仍落在膚
色帶內的目標——(252,216,208) 本身暖度 44（帶是 [22,48]）、最亮通道 252（下限
245），兩個都在帶內——所以同一輪的
`test_skin_texture_keeps_visible_tone_under_mtoon_lighting` 與
`test_face_texture_keeps_the_contrast_its_features_live_in` 都是綠的，只有這一
條紅。

餘裕要說清楚：4.38 對上限 3.0 只有 1.46 倍，因為 M11 只把目標挪了 6 個通道單
位。真正壞掉的情形（兩張各解各的，如 `baseline.vrm` 的 15.77）離上限有 5.3
倍。
