# Mika 人格導入 — 語音與文字的語氣統一

## 背景

2026-08-26 盤點 chatbot 的十層語氣來源後發現：Mika 的人格只存在於預錄語音
（`scripts/voice_lines.py`，25 句 × 3 語，辣妹語調滿載），文字回答則完全沒有語氣指示。
同一個角色，說話跟打字像兩個人。

三個實質缺陷：

1. **`converse` 節點是身分破口**（`rag/nodes.ts:339`）。它的 system prompt 自稱
   "Charles Chen's portfolio assistant"，沒有任何 Mika 指示，所以訪客一問
   「我剛剛問了什麼」，她就退回成通用助理。這違反 memory `feedback_mika_first_person`。
2. **罐頭招呼語與語音自介互相矛盾**（`rag/triage.ts` `FAQ[]`）。點她會聽到她自報名字，
   打字說 hi 卻得到「我是 Charles 的作品集小助手」。
3. **FAQ cache 57 條有 53 條沒有 Mika 視角**（`rag/faq-cache.ts`）。這層原文返回不經 LLM，
   改 prompt 對它完全無效。

## 角色定位（使用者 2026-08-26 定案）

**Mika 是 Charles 的頭號粉絲兼經紀人，替他講他自己不好意思講的話。**

這個定位解決 portfolio 的核心張力：主要讀者是 recruiter，自我推銷顯得自誇，換成角色推銷就成立，
而且她回答的正確性本身就是 Charles 工程能力的展示品。

外貌依據（從 `public/avatar/AvatarSample_B_webp.vrm` 貼圖實際查證）：紫黑漸層長髮加青藍挑染、
紅藍 X 型髮夾、星星髮飾與黑色蝴蝶結、金色瞳孔配粗眼線、眼下星星貼鑽、黑皮革扣環項圈、
深藍緞面棒球外套、小麥膚色。地雷系與原宿辣妹的混合路線，配 VOICEVOX 春日部つむぎ辣妹聲線。

四個特質：

1. **直球自豪**：主動把最強的數字推到前面。
2. **驕傲有出處**：每次自豪綁一個數字或來源；資料沒有就直說，絕不腦補。
3. **熟人語感**：台灣口語與句尾語氣詞，不堆敬語。
4. **有自我意識**：知道自己是 corrective RAG 並拿它當賣點；被挑釁會嗆回去。

反向規則（比特質更重要）：不為賣萌犧牲資訊密度；每則最多 1 個 emoji；不用撒嬌自貶；
引用規則與拒答規則一字不動。

## 強度分層

| 層 | 強度 | 表現 |
|---|---|---|
| 招呼、道別、擋注入 | 100% | 完整角色語氣 |
| 身分題（她是誰、怎麼做的） | 70% | 開場自介帶語氣，技術內容照舊嚴謹 |
| 內容題（經歷、專案、能力） | 20% | 首句與末句帶語氣，中段維持簡報體 |
| 拒答、隱私導向 | 40% | 得體優先，語氣點到為止 |

## 三語策略（使用者定案）

各語獨立改寫，比照 `voice_lines.py` 既有做法（按 JOB 重寫，不直譯）：
zh-TW 走台灣口語語氣詞、ja 走 gyaru 語體、en 走 casual American。

## 驗收標準

1. 訪客用任一語言問「你是誰」，不論命中 FAQ cache 或走 generate，回答都以第一人稱 Mika 開場。
2. 訪客問「我剛剛問了什麼」（converse 路徑），回答仍是 Mika，不會退回成通用助理。
3. 打字說 hi 得到的招呼語與語音自介是同一個角色。
4. FAQ cache 的內容題答案首末句帶 Mika 語氣，中段的粗體、條列、數字結構不變。
5. 拒答與隱私導向仍然得體，語氣不干擾內容。
6. 語氣定義有單一擁有者，`converse` 與 `generate` 兩個 prompt 消費同一份定義；
   刪掉任一邊的接線，測試會紅。

## Non-goals

- 不改語音台詞與音檔（已定案且已錄製）。
- 不改引用規則、拒答規則、注入防禦 regex、scope 限制。
- 不改 FAQ cache 的事實內容與數字，只改首末句的語氣包裝。
- 前端介面文案（`src/i18n/strings/*.ts` 的 `chat.*`）預設不改，但**她的台詞不算介面文案**：
  第六輪與第十二輪各跨過一次，改動範圍與理由記在那兩節。`chat.*` 三語共 120 條文案，到
  第十三輪為止被改寫的是 8 條，落在 3 個鍵上：`emptyMessage`（三語）、`errorMessage`
  （三語）、`avatarBubble`（ja 的人稱、zh 的句尾助詞）。其餘 37 個鍵未動。
- 不做即時 TTS。

## PASS 的定義（2026-08-27 訂，第十八輪起生效）

**凍結的範圍是判準，措辭則會被修。** Gate A 的四項、Gate B 的範圍與 BLOCKING／
ADVISORY 分級、PASS＝BLOCKING 為零，這三項的實質不因輪次而改。措辭則每輪都動：多數是
把敘述改成與程式碼相符或拿掉禁用句式，也有純補充（第十九輪補上數字檢查反向那半的說明，
第二十輪在 Gate C 寫明「修正 BLOCKING 時可改寫既有段落」這個例外，第二十一輪寫下這一段
本身，第二十二輪在 Gate A 那格註明 `rag:test` 的 glob）。這些補充都沒有動到通過條件。
判準本身要改，得先在這裡寫明改了什麼、為什麼。

第十三到十七輪連續五輪 FAIL，發現全落在散文與命名準確度。診斷出來的原因有三個，
都是流程本身造成的，不是產出本身還壞著：

1. **每輪產出新的可審查散文。** 那五輪我每輪往這份 plan 新增 43 到 128 行敘述，
   平均 65.4 行（`git show --numstat` 的新增行數，五輪同一基準）。每一行都是新的
   可被證偽的宣稱。第十四輪起，每輪的發現有 40% 到 50%
   是**上一輪的修正本身造成的**（重排註解留下孤行、數字在一段改對另一段沒改、
   為修語體而寫的段落自己跳語體）。修得比生得慢，所以永遠不會收斂。
2. **我讓判準 drift。** 第十二輪起我在 reviewer prompt 裡加了「主動找同類的其他實例」，
   把範圍從本輪 diff 擴大到全 repo 的散文。範圍每輪變大，PASS 就退後一輪。
3. **這三類缺陷沒有機械防線。** 行寬與孤行、註解裡的數字、user-facing 禁用句式，
   全靠人眼。人眼每次只找得到兩三個，找到就 FAIL。

所以 PASS 從「兩位 reviewer 都挑不出東西」改成下面三道可判定的閘門。

### Gate A：機械檢查，四項全綠

| 指令 | 通過條件 |
|---|---|
| `npx tsc -b` | exit 0（不是 `--noEmit`，根 tsconfig 是 `files: []` 的 solution 檔，`--noEmit` 什麼都不檢查） |
| `npm run rag:test` | 0 fail。它的 glob 含 `rag/**/*.test.ts`，會一併跑到工作樹上與本工作無關的 `rag/insights/*.test.ts`，所以本工作自己的數字要看 `npx tsx --test rag/*.test.ts` |
| `npm test` | 0 fail |
| `python3 <scratch>/mutate_r5.py` | 每條都有 fail、零 ABORT |

第三類缺陷在這一輪變成 `rag/prose-lint.ts` 與 `rag/prose-lint.test.ts`，跑在
`rag:test` 裡，涵蓋 `persona.ts`／`prose-lint.ts`／`prose-lint.test.ts`／
`faq-audit.test.ts`／`nodes.test.ts`／`triage.test.ts`／`chatVoice.test.ts` 的每一行
註解：整行 `//`、`/** */` 區塊裡的每一行、以及行尾註解（`isProseLine` 與
`trailingComment` 決定，區塊的起訖符號不算）。孤行那一項只套用在整行註解上，因為行尾
註解不是折行的段落。受檢的文案是 `mika-persona` changelog 三語與 `chat.*` 三語的每一
個字串。

綠要有意義，靠兩層：每個檢查器各有用壞輸入驅動的測試（第十七輪那些孤行與過長行的
原文、差點出貨的 `ではなく` 段落、第十輪那個「52 應為 53」的形狀，以及禁用清單裡
**每一個** alternation 分支各一條），而掃過真實檔案的每一條斷言各有一條資料側
mutation：往 `persona.ts` 插一行過寬註解、往 `nodes.test.ts` 插一個未申報數字、
把一個真的 docblock 用插入的函式擠開、
往日文 changelog 的 `mika-persona` entry 最後一段散文插一句 `ではなく`（該處在切片的
91.8%，所以它證明的是切片至少延伸到那裡）。

數字那條還有反向的一半：宣告了卻沒有任何註解引用的數字也會紅。少了它，一個死宣告會
把那個數字對未來的註解永久豁免，而且它本身就是一句假的敘述。

### Gate B：reviewer 的範圍與分級（凍結）

- **審查對象**＝本輪 diff，以及 diff 觸及的檔案。**不含**本輪沒有觸及的檔案裡的既有散文。
- 發現分兩級：
  - **BLOCKING**：(a) 行為缺陷；(b) 新增或改寫的斷言沒有 mutation 覆蓋，或既有覆蓋被縮小；
    (c) 本輪 diff 新增或改寫的句子與現行程式碼矛盾；(d) 上述三個機械類別的實例被檢查漏掉
    （這種要同時說明檢查該怎麼改才抓得到）。
  - **ADVISORY**：其餘一切，包含未觸及檔案的既有散文、風格偏好、可讀性建議。
- **PASS 條件：BLOCKING 為零。** ADVISORY 不阻擋，列出來交給使用者決定要不要另開一輪。

這不是放寬。第十一輪原本就是 diff 範圍，是我在第十二輪自己加指示把它擴大的；而擴大出去
的那三類，現在改由機械檢查涵蓋整組檔案，比人眼抽查嚴格。

## 2026-08-26 雙 reviewer 第一輪：兩份 FAIL 與處置

兩個 fresh-context reviewer 獨立稽核，各自 FAIL，發現不重疊的部分都成立。

### 已修

1. **`MIKA_VOICE` 的來源條款與 `converse` 的規則互相矛盾。**
   原文寫「back every one of them with a number or a source」與「traces to the context
   or the portfolio map」，但 `converse` 沒有編號 context 也沒有 portfolio map，它的規則是
   「只從 transcript 回答」。更要緊的是 `converse` 只跑 `stripUngroundedLinks`，沒有
   `stripInvalidCitations`，所以被這條逼出來的 `[1]` 會原樣送到訪客眼前。
   改成不指名來源，並明說這個區塊不新增任何引用要求。

2. **`personalRedirect` 違反 persona 自己的 emoji 規則。**
   規則原文禁止「declining a genuine request」時用 emoji，而問「他幾歲」確實是 genuine
   request 被 decline，三語卻都帶著 😊。判定是規則寫得太粗：作品集查不到與拒絕越界請求
   要讀起來直白，擋注入與把私人問題轉交本人這兩個場合的溫度本身就是內容。規則改寫成
   四個場合各自指名，測試也拆成兩條，各自釘住「零個 emoji」與「恰好一個 emoji」。

3. **`rag/nodes.ts` 的 output-guardrail 罐頭回覆漏掉了。**
   它是第三個不經模型的字串（另外兩個在 `triage.ts`），先前是無名的，zh-TW 版還帶著
   半形逗號。連同 scope-lock 裡給模型看的拒答範例一起改成她的語氣。

4. **`MIKA_IDENTITY` 內部自相矛盾。** 「She is the chat launcher…」出現在
   「never describe Mika in the third person」的前一句。這段是從 `nodes.ts` 原封搬過來的，
   所以矛盾也跟著搬。改成第一人稱。

5. **內容題只有開場句，沒有結尾句。** 這是驗收標準 4 的一半，兩個 reviewer 都指出。
   52 條補上三語結尾句（另 5 條本來就以邀請收尾），並補一條測試釘住。

6. **15 條開場句與內容首句重複。** 「四條原則，他是真的照著做。」接「Charles 有四個工作原則：」
   這類。改寫成帶她的態度而不重述答案。

7. **6 處日文開場句掉了主語，把 Charles 的事變成她的事。**
   「これは自分のために作ったツールなので」會讀成 Mika 為自己做的。日文可以省略主語，
   而省略的主語會接到前一個說話的人身上，所以這類句子必須顯式寫出「彼」。

### 已知限制，刻意留著

- **開場句與結尾句的測試對「內容段本身就很短」的條目無效。**
  實測（不是估計）：刪掉開場句在 171 個答案／語言組合中有 53 個不會被抓到，刪掉結尾句有 33 個。

  讓型別在編譯期強制；那會改變 `answers` 的語意並牽動 ingest 與既有測試，本輪不做。
  翻開條件：再出現一次「新條目忘了寫語氣句」。
- **`injectionRefusal` 的日文用常体，其他說明類文案用敬体。**
  這是 100% 強度那一層，情緒句用常体貼近錄音，符合分層表。

## 2026-08-26 雙 reviewer 第二輪：兩份 FAIL，六個發現

最要緊的兩項有同一個根因：**我在文件裡宣稱了程式碼沒做到的事**。

1. **三語 changelog 寫「現在每一句日文都會把あたし留著」，實測 57 條日文答案有 31 條

### 一、三條 regex 各有可構造的逃逸與誤判

reviewer 直接給出字串，我逐條實測確認：

| regex | 逃掉的（應該抓） | 誤殺的（不該抓） |
|---|---|---|
| `JA_POLITE_ENDING` | でしょう。／でしょうか？／いきましょ！ | ますます／励ますんだ／だますわけ |
| `ZH_SPOKEN_ENDING` | 這比數量更重要！（任何句子加驚嘆號都過） | 哦／呦 這類常見台灣語氣詞 |
| `ZH_PARTICLE_AT_CLAUSE_END` | 呢／吧／嗎 疊用（不在字集裡） | 四字語助詞「哎唷喂呀，」 |

日文那條的根因是**判準挑錯位置**：第五輪改成「不限位置比對」，於是只能靠
`(?![ょぐ])` 這種補丁擋誤殺，而補丁擋不住 でしょう。正確的判準是**敬体語尾後面接什麼**：
接標點或終助詞就是敬体，接 ん／わ／ま／ぐ 就是碰巧含到那些字的常体動詞。改成

```
/(?:です|ます|ません|でした|ました|ましょう|ましょ|ください|でしょう)(?=[。！？、）\s]|[よねかがからのでけどしなぞぜ]|$)/
```

新舊對照實測：11 個該抓的全抓到（舊的漏 3 個），8 個不該抓的全放過（舊的誤殺 3 個）。
已知極限寫進註解：〜ませ（いらっしゃいませ）沒列，因為 ませ 也出現在常体的「済ませて」。

中文那條移掉了「單靠驚嘆號就算口語」的分支，只有一條結尾句靠它通過，一併改成有語氣詞收尾。
